# 전체 아키텍처

`docs/decisions.md`에 흩어진 결정들을 하나의 그림으로 묶은 문서.
세부 근거·실측 수치는 각 결정 항목을 참고하고, 여기서는 "무엇이 무엇을 어떻게 부르는지"만 다룬다.

## 전체 그림

```
┌─────────────────────────────────────────────────────────────┐
│  Claude Code (터미널 CLI 또는 데스크톱 앱)                      │
│                                                                │
│  ┌──────────────┐         ┌──────────────┐                   │
│  │  Stop 훅      │         │ Notification │                   │
│  │ hooks/on-stop│         │ hooks/on-     │                   │
│  │             │         │ notification  │                   │
│  └──────┬───────┘         └──────┬───────┘                   │
│         │ 로컬 TCP 소켓(127.0.0.1:고정포트)로 "요약 텍스트" 전달   │
└─────────┼─────────────────────────┼──────────────────────────┘
          │                         │
          ▼                         ▼
┌─────────────────────────────────────────────────────────────┐
│  상주 리스너 프로세스  voice/listener.py  (하나만 계속 떠 있음)    │
│                                                                │
│  - 로컬 TCP 서버: 훅으로부터 "이런 일이 있었다" 텍스트 수신          │
│  - TTS 재생 (voice/tts.py, sherpa-onnx)                       │
│  - 항상 마이크 열어두고 VAD(Silero) + 호출어 감지(local-wake)     │
│  - 호출어 감지("자비스") → 받아쓰기 모드 진입 → STT(whisper.cpp)  │
│  - STT 결과 텍스트를 voice/inject.js 호출로 Claude Code 세션에    │
│    postback (cross-session messaging 소켓, 실측 검증 완료)      │
│  - 상태 관리: 유휴 / TTS재생중 / 받아쓰기중 (한 프로세스 안 변수)   │
└─────────────────────────────────────────────────────────────┘
          │
          │ (STT 결과 postback, node 프로세스 spawn)
          ▼
┌─────────────────────────────────────────────────────────────┐
│  voice/inject.js (Node, 상주 프로세스가 필요할 때마다 실행)        │
│  - CLAUDE_CODE_MESSAGING_SOCKET/TOKEN 읽어 named pipe 연결      │
│  - auth+user 두 줄을 한 번의 write()로 합쳐 전송 (검증된 프로토콜) │
└─────────────────────────────────────────────────────────────┘
```

## 프로세스 경계와 이유

| 경계 | 이유 |
|---|---|
| 훅(Python, 짧게 실행 후 종료) ↔ 상주 프로세스(계속 떠 있음) | 훅은 Claude Code가 매번 새로 실행하는 단발성 프로세스라 무거운 모델(whisper 로딩 16.7초 등)을 매번 들고 있을 수 없음. 무거운 건 상주 프로세스가 미리 로딩해둔다 |
| 상주 프로세스(Python) → inject.js(Node) | Cross-session messaging의 실제 프로토콜(named pipe, 특정 write 방식)이 Node 환경에서 먼저 검증됐고, Claude Code 자체가 Node 기반이라 관련 예제도 Node. Python에서 Windows named pipe를 직접 다루는 것보다 검증된 Node 스크립트를 그대로 spawn하는 쪽이 리스크가 낮음 |
| 훅 → 상주 프로세스: 로컬 TCP 소켓 (파일 감시 아님) | 즉시 반응 + 상주 프로세스가 꺼져 있으면 `ConnectionRefusedError`로 바로 알 수 있음 (2026-09-25 결정) |

## 데이터 흐름 (이벤트별)

### 1. 작업 완료 → 음성 요약
1. Claude Code가 응답을 마치면 Stop 훅 실행 (`hooks/on-stop.py`)
2. 훅이 stdin JSON에서 `last_assistant_message` 필드를 그대로 읽음 (실측 확인됨, `transcript_path` 파싱 불필요)
3. 훅이 로컬 TCP 소켓으로 상주 프로세스에 그 텍스트를 전달하고 즉시 종료
4. 상주 프로세스가 `voice/tts.py`로 음성 요약 합성 후 재생
5. **Claude Code 공식 터미널 벨 알림을 음성 요약과 병행 재생할지 여부**는 사용자가 설정으로 켜고 끌 수 있음 — 새 비프음을 우리가 만드는 게 아니라, 이미 있는 공식 기능(벨)을 그대로 쓸지 끌지 선택하는 것. 끄는 방법은 Claude Code 자체 설정(터미널 벨 옵션)을 그대로 안내하거나, 이 프로젝트 설정에서 병행 여부만 문서화하는 두 방식 중 미정

### 2. 권한 요청 → 알림
- 동일 구조, `hooks/on-notification.py` → 상주 프로세스 → 짧은 TTS 안내

### 3. 유휴 상태에서 호출어로 명령
1. 상주 프로세스가 항상 마이크를 열어 VAD + local-wake로 "자비스" 감지 대기
2. "자비스" 감지 → 받아쓰기 모드 진입 (짧은 신호음 또는 TTS로 "네" 등 피드백 — 세부 미정)
3. 발화 종료(VAD로 침묵 감지) → 녹음된 오디오를 whisper.cpp(`language='ko'` 고정)로 텍스트화
4. 텍스트를 `voice/inject.js`로 postback → Claude Code 세션에 사용자 메시지로 도착
5. 기존 작업 중이었다면 중단하지 않음(2026-09-25 결정: 트리거 로직)

### 4. TTS 재생 중 사용자가 말을 시작 (바지-인)
1. 상주 프로세스가 TTS 재생 중에도 VAD를 계속 돌림
2. VAD가 발화 감지 → 호출어 없이 즉시 TTS 중단 + 받아쓰기 모드 진입
3. 이후는 위 3번 흐름과 동일

## 아직 정해지지 않은 것 (다음 설계 대상)

| 항목 | 현재 상태 |
|---|---|
| 로컬 TCP 소켓 포트 번호, 메시지 포맷(JSON 스키마) | 미정 — "TCP 소켓으로 한다"만 확정 |
| 작업 완료 시 Claude Code 공식 터미널 벨을 음성 요약과 병행 재생할지 여부 | **켜고 끌 수 있는 설정으로 확정** (2026-09-26). 새 비프음을 만드는 게 아니라 기존 공식 벨 기능의 on/off 선택. 기본값, 설정 키 이름은 미정 |
| 받아쓰기 모드 진입/종료 시 사용자 피드백(신호음? 짧은 TTS?) | 미정 |
| 상주 프로세스 시작/종료 방법 (`/voice-on`, `/voice-off` 스킬이 어떻게 프로세스를 관리하는지 — OS 프로세스 spawn? Windows 서비스?) | 미정, 2026-09-25 발언에서 언급만 됨 |
| 설정 파일 구조(`.claude/settings.json`에 음성 on/off, 벨 병행 여부 등을 어떤 키로 저장) | 미정 |
| 상주 프로세스가 죽었을 때 훅의 동작 (조용히 무시? 터미널 벨로 폴백?) | 미정 — `ConnectionRefusedError` 감지까지는 결정됨, 그 다음 행동은 미정 |
| `setup.*` 설치 스크립트가 known-issues.md의 7개 우회를 어떻게 자동화할지 | 미정 |
