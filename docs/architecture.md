# 전체 아키텍처

`docs/decisions.md`에 흩어진 결정들을 하나의 그림으로 묶은 문서.
세부 근거·실측 수치는 각 결정 항목을 참고하고, 여기서는 "무엇이 무엇을 어떻게 부르는지"만 다룬다.

## 프로젝트 성격 (2026-09-26 재정의)

이 프로젝트는 "눈이 안 좋은 사람"에 국한되지 않는다. 기본 가치는 **화면을 안 보고도 여러 프로젝트를
동시에 음성으로 지휘하는 비서** — 접근성은 그 일반 기능의 자연스러운 부분집합이다. 사용자가 다른
작업을 하며 여러 Claude Code 세션(프로젝트별)에 음성으로 지시하고, 각 세션이 끝날 때마다 상주
에이전트 하나가 순차적으로 음성 요약을 들려주고, 음성 명령은 올바른 세션으로 라우팅한다.

## 다음 설계: 판단 3단계 + 파일 기록 + 서브 관리자 (2026-11-20 확정, 1~4단계 구현됨 — 실제 마이크·여러 세션 확인 전)

이 절이 지금 구조다. 아래 "전체 그림"부터는 **2026-11-20 이전 구조(기록용)**이고, 이 절과 어긋나는 부분
(TCP 전달, 규칙만 쓰는 라우팅, "멈춰" 전체 전달, `/voice-detach`·`/voice-attach`)은 이 설계로 대체된다.

### 왜 바꾸나
처음 원칙은 "리스너는 말뜻을 이해하지 않는다"였다. 그래서 판단을 다른 곳으로 미뤘다 —
"멈춰"는 모든 세션에 보내 각자 판단, 멈춘 세션은 스스로 detach 스킬 호출, 프로젝트 지정은
"문장이 폴더명으로 시작할 때"만. 그런데 폴더명은 영어(`eyes-free-coding`)이고 받아쓰기는 한국어라
**말로는 사실상 프로젝트를 고를 수 없었다**(늘 "방금 알림 온 세션"으로 감). 판단을 싸게 맡길 수
있는 Jev가 생겼으니 리스너가 직접 판단한다.

### 판단 3단계 (싼 것부터, 확신이 낮을 때만 다음으로)
1. **규칙** — 무료·즉시. 괄호만 있는 받아쓰기("(음악)")는 잡음, 세션이 하나뿐이면 대상 고정 등.
2. **Jev** — 거의 무료·약 0.3초. 받아쓴 문장 + 상황(열린 세션 목록과 각 마지막 요약)을 넘기고
   한 번의 호출로 "무슨 명령인가"(choice)와 "대상"(세션 하나 / 전체 / 리스너 자신 / 모름)을 같이 받는다.
   확신도가 기준선(처음 0.8, 실사용 로그로 조정) 이상이면 그대로 실행.
3. **서브 관리자(Haiku)** — Jev가 애매하다고 한 것, 그리고 Jev가 못 하는 **글 만들기**(밀린 기록 요약,
   여러 기록을 한두 문장으로 묶기, 전체 지시 확인 문장)를 맡는다. 본인도 모르면 되물을 문장
   ("번개장터요, 축구요?")을 돌려주고 리스너가 읽어 준다.
- 키가 없거나 Jev·서브 관리자가 응답하지 않으면 지금 규칙(방금 알림 온 세션)으로 돌아간다.

### 명령 목록
| 명령 | 예시 | 대상 | 동작 |
|---|---|---|---|
| 지시 (기본) | "번개장터 봇에 키워드 추가해" | 세션 하나 | 그 세션에 전달 |
| 멈춰 | "번개장터 멈춰" | 세션 하나 | 그 세션에 **그냥 메시지로 전달**(아래 참고), 리스너가 그 세션을 "멈춤"으로 표시해 다시 부르기 전까지 기본 대상에서 뺌 |
| 전체 멈춰 | "전부 멈춰" | 전체 | 열린 모든 세션에 "멈춰" 전달 (확인 없이) |
| 전체 지시 | "다들 커밋하고 정리해" | 전체 | **확인 후** 전달: "프로젝트 3개에 '…'를 보낼까요?"를 읽고 "응"이면 전달 |
| 다시 시작 | "번개장터 계속해" | 세션 하나 | 멈춤 표시를 풀고 전달 |
| 상황 묻기 | "번개장터 어떻게 됐어?" | 리스너 | 그 프로젝트 기록을 읽어 줌(여러 개면 서브 관리자가 묶음) |
| 밀린 거 듣기 | "나 없는 동안 뭐 했어?" | 리스너 | 안 들은 기록을 서브 관리자가 요약해 읽어 줌 (구 Catch me up) |
| 다시 말해줘 | "방금 거 다시" | 리스너 | 마지막 안내를 다시 읽음 |
| 목록 | "뭐 열려 있어?" | 리스너 | 열린 프로젝트 이름을 읽어 줌 |
| 조용히 / 다 알려줘 | "조용히 해" | 리스너 | 조용히 모드: 실패·질문만 읽고 나머지는 기록만 (구 Listening modes, 수동 전환) |
| 취소 | "아니야, 취소" | 리스너 | 방금 받아쓴 말을 버림 (삑 두 번) |
| 잡음 | (환각·잡소리) | — | 버림 (삑 두 번) |

- **권한 확인 창에는 말로 답할 수 없다** — 화면 버튼이고, 주입한 메시지는 승인으로 인정되지 않는다. 그래서 목록에 없다.
- **"멈춰"는 작업을 강제로 끊지 않는다(확정)**: 주입한 메시지는 일하는 중에 도착하지만 "지금 하던 일을
  마친 뒤 처리하라"는 안내가 붙어 온다(2026-11-20 이 프로젝트 세션에서 실제로 받아 본 형태). 그래서 받은
  세션은 하던 단계를 정리하고 멈춘다. 파일을 반쯤 고친 채로 끊기는 것보다 안전하다. 강제 중단용
  PreToolUse 훅 안은 검토 후 버렸다.

### 파일 기록 (`~/.voxcode/`)
| 파일 | 쓰는 쪽 | 내용 |
|---|---|---|
| `log.jsonl` | 리스너 | 모든 사건을 한 줄씩 덧붙임: 받아쓴 말, 판단 결과(누가 판단했나·확신도), 전달 대상, 완료 요약. "밀린 거 듣기"·"상황 묻기"의 원본이자 기준선 조정 자료 |
| `state.json` | 리스너 | 지금 상황 스냅숏: 열린 세션(프로젝트명·소켓·마지막 요약·멈춤 여부), 조용히 모드, 서브 관리자 연결 정보 |
| `inbox/*.json` | 훅 | 세션의 완료·알림 요약. 리스너가 폴더를 지켜보다 읽어 감 — 리스너가 꺼져 있어도 사라지지 않음 |

- 말한 내용은 **파일에 먼저 기록한 뒤** 전달한다. 기록이 진실의 원본이다.
- 훅 → 리스너를 TCP 대신 `inbox/` 파일로 바꾸면 TCP 서버·포트·연결 타임아웃이 빠진다. 켜고 끄기
  확인은 `state.json`의 리스너 PID로 한다.
- 세션에 넣는 메시지에는 그 세션의 소켓 토큰이 필요하다 — `state.json`에 토큰이 남는다(사용자 폴더 안,
  같은 사용자만 읽음).

### 서브 관리자 (Haiku, 계속 켜 둠 — 사용자 결정)
- **계속 켜 둔 Claude Code 세션 하나**: 전용 폴더 `~/.voxcode/manager/`에서 Haiku 모델로 실행한다.
  계속 켜 두는 이유: 상황을 기억한 채로 판단해야 더 똑똑하다(사용자 결정, 2026-11-20).
- **처음에 상황 인지**: 그 폴더의 `CLAUDE.md`에 역할과 답하는 형식을 적어 둔다("너는 음성 명령 중재자다.
  `~/.voxcode/state.json`을 먼저 읽어라. 판단 결과는 정해진 JSON 형식으로 파일에만 써라. 코드를 고치지
  마라"). 시작할 때 첫 지시로 상황 파일을 읽힌다.
- **띄우기**: `/voice-on`이 새 콘솔 창으로 실행(예:
  `start "Voxcode 관리자" /D %USERPROFILE%\.voxcode\manager cmd /k claude --model claude-haiku-4-5 "상황 파일을 읽고 대기해"`).
  관리자 세션은 시작·응답 종료 때 자기 소켓·토큰을 `state.json`에 등록한다(그 폴더 전용 훅).
- **주고받기**: 리스너가 질문(id, 받아쓴 말, Jev 판단과 확신도, 최신 상황)을 관리자 세션에 주입 →
  관리자가 `~/.voxcode/manager/answers/<id>.json`에 답을 씀 → 리스너가 그 파일을 기다림(제한 시간
  약 20초, 넘으면 규칙으로 돌아가고 삑 두 번).
- **열린 문제**: 대화가 계속 쌓이므로 가끔 비워야 한다(예: 하루 한 번 재시작 또는 질문 N개마다 `/clear`
  안내). 관리자 세션도 Claude Code라 사용자 전역 훅(완료 전 verify 요구 등)이 같이 돈다 — 코드를 안
  고치므로 문제없을 것으로 보지만 만들 때 확인. 별도 Claude 실행이 필요하므로 CLI 로그인이 살아 있어야
  한다(2026-11-20 headless 실행이 "OAuth session expired"로 실패한 적 있음).

### 듣기 (세션 → 사용자)
- 훅이 완료·알림 요약을 `inbox/`에 쓴다 → 리스너가 읽어 `log.jsonl`에 기록 → Jev가 종류(완료/실패/
  질문·승인 대기/진행 중)를 고름 → 읽을지 결정: 실패·질문은 바로, 완료는 받아쓰는 중이면 미룸,
  조용히 모드면 실패·질문만 읽음.
- 처음 1주는 Jev 판단을 **기록만** 하고 읽는 동작은 지금처럼 두었다가, 규칙보다 나은 게 보이면 적용.

### 설치 범위 (함께 바꿀 것)
- 지금 훅은 이 프로젝트의 `.claude/settings.json`에만 등록돼 있어 **다른 프로젝트 세션은 알림을 보내지
  않는다**. 여러 프로젝트를 지휘하려면 훅을 사용자 전역 설정(`~/.claude/settings.json`)에 등록해야 한다
  (`/voice-on`이 등록·해제를 맡는 안).

### 만드는 순서 (단계마다 verify + 실제 실행 확인, 커밋 하나씩)
1. 말하기: `log.jsonl`·`state.json`, Jev 판단(명령+대상), 지시·멈춰·전체 멈춰·다시 시작·취소·잡음,
   브로드캐스트·`/voice-detach`·`/voice-attach`·폴더명 시작 규칙 제거
2. 리스너가 직접 처리하는 명령: 목록·다시 말해줘·조용히·상황 묻기(기록 그대로 읽기)
3. 서브 관리자: 띄우기·등록·질문/답 파일·제한 시간 폴백, 밀린 거 듣기·전체 지시 확인 문장
4. 듣기: 훅 → `inbox/` 파일, Jev 종류 판단(처음엔 기록만), TCP 서버 제거, 훅 전역 등록

### 1단계 구현 메모 (2026-11-20, `voice/judge.py`·`voice/record.py`·`voice/listener.py`의 `route_and_send`)
- **흐름**: 받아쓴 문장 → `log.jsonl`에 `heard` → `judge()`(규칙 → Jev 한 번) → `decision` 기록 → 멈춤 표시 변경
  → 전달 → `sent` 기록. 버린 문장은 `dropped`. 완료 알림은 `notify`로 기록.
- **확신 판정**: 명령·대상 각각 확신도 0.8 이상일 때만 Jev 판단을 따른다. 세션이 하나뿐이면 대상은 규칙으로 그 세션.
- **폴백**(키 없음·오류·명령 확신 부족): 멈춤 단어("멈춰·그만·스톱·중지")가 있으면 세션 1개일 때만 그 세션을
  멈추고, 아니면 **아무것도 안 보내고 삑 두 번**. 그 외 문장은 지시로 보고 규칙(세션 1개 → 멈추지 않은 세션 중
  최근 완료 알림 → 최근 명령)으로 보낸다.
- **명령별**: 지시는 Jev가 고른 세션(확신 부족·all·listener·unknown이면 규칙 폴백, 멈춘 세션을 직접 부르면 멈춤 해제) /
  멈춰는 대상 확정 시 그 세션 하나에 문장 그대로 전달 + 멈춤 표시, 애매하면 아무것도 안 함 + 삑 두 번 /
  전체 멈춰는 모든 세션 전달 + 모두 멈춤 / 다시 시작은 대상 확정(또는 멈춘 세션이 하나뿐) 시 해제 + 전달 /
  취소·잡음은 버림 + 삑 두 번. 전체 지시는 2·3단계라 이번엔 지시와 같게 규칙 폴백.
- **멈춤 해제 조건**: 다시 시작, 그 세션을 향한 확신 있는 지시. **완료 알림(notify)으로는 풀리지 않는다.**
- **외부 전송**: Jev에는 받아쓴 문장과 프로젝트명·마지막 요약(300자)만 간다. 세션 key(소켓 경로)·토큰은 `s1, s2…`로 바꿔 보낸다.
- **state.json**: 테이블이 바뀔 때마다 임시 파일 → `os.replace`로 덮어쓴다. 이번 단계는 쓰기만 하고 시작 시 복원하지 않는다.
- 제거: "멈춰 {프로젝트}" 전 세션 브로드캐스트, `/voice-detach`·`/voice-attach` 스킬과 리스너 detach/attach 이벤트,
  "문장이 폴더명으로 시작" 규칙, 환각 필터(`hallucination_score` — 잡음 판단이 명령 판단에 합쳐짐).

### 2단계 구현 메모 (2026-11-20, `_listener_reply`·`ListenerContext`)
- 목록·다시 말해줘·조용히·다 알려줘·상황 묻기는 세션에 보내지 않고 리스너가 읽어 준다(`say`). 삑 없음.
- 상황 묻기는 기록 그대로: 대상 세션 하나면 그 세션의 마지막 요약, 아니면 모든 세션 요약을 이어 읽는다.
- 조용히 모드는 `state.json`의 `quiet`. Jev 종류 판단(4단계)을 적용하기 전까지는 **훅 종류로 거른다**:
  Notification 훅(권한·질문)은 읽고 Stop 훅(완료 요약)은 기록만.
- "다시 말해줘"는 TTS가 마지막으로 읽기 시작한 문장(`ctx.last_said`).
- 확신이 낮으면 이 명령들도 1단계와 같이 규칙 폴백(세션에 전달)된다 — 3단계 서브 관리자가 메운다.

### 3단계 구현 메모 (2026-11-20, `voice/manager.py`)
- **언제 묻나**: Jev 판단 불가·명령 확신 부족, 또는 멈춰·다시 시작의 대상이 애매할 때(세션 2개 이상). 지시의
  대상 애매는 묻지 않고 규칙("방금 알림 온 세션")으로 간다 — "응", "1번" 같은 짧은 대답마다 최대 20초를 기다리지 않게.
- **질문 파일**: `~/.voxcode/manager/questions/<id>.json` — 받아쓴 문장, Jev 판단, 세션(프로젝트명·멈춤·요약),
  최근 기록 20개. 소켓·토큰은 넣지 않는다. 관리자 세션에는 `[Voxcode 질문 <id>]` 한 줄만 주입한다.
- **답**: `judge` → `{"command","target"(프로젝트명/all/listener/unknown),"ask_back"}`, `summarize` → `{"say"}`.
  대상을 모르고 `ask_back`이 있으면 그 문장을 읽고 아무 데도 보내지 않는다(삑 없음).
  프로젝트명이 정확히 하나와 맞지 않으면 대상 애매로 본다.
- **시간 초과(20초)·관리자 없음**: 1단계 폴백 그대로. 무언가 보냈으면 삑 없음, 아무 데도 안 보냈을 때만 삑 두 번
  (설계 초안의 "넘으면 삑 두 번"을 "삑 두 번 = 아무 데도 안 보냄" 규칙에 맞춤).
- **전체 지시**: 확인 문장은 템플릿("프로젝트 N개에 '…'를 보낼까요?") — 관리자에게 맡기면 매번 최대 20초가 더 든다.
  30초 안에 "응·네·그래·보내"면 멈추지 않은 세션 모두에 전달, "아니·취소"면 버림, 다른 말이면 확인을 버리고 평소대로.
- **밀린 거 듣기**: 마지막으로 들은 시각(`state.json`의 `last_catchup`) 뒤의 `notify` 기록을 관리자가 요약.
  관리자가 없으면 최근 5개를 그대로 읽는다. **상황 묻기(여럿)**도 관리자가 묶고, 못 하면 이어 읽기.
- **관리자 세션**: 폴더 `~/.voxcode/manager/`(역할 `CLAUDE.md`, 권한 `.claude/settings.json` — questions 읽기·answers 쓰기만),
  `claude --model haiku --permission-mode acceptEdits`, 새 콘솔 창, cmd PID를 `pid` 파일에. 전역 Stop 훅이 그 폴더에서는
  프로젝트로 알리지 않고 `session.json`(소켓·토큰)만 등록한다. 역할 문서에 사용자 전역 지침의 작업 절차(하네스 자동 적용,
  /phm-delegate 제안, verify 보고 등)를 적용하지 말라고 적었다.
- **미검증(실제 실행 전)**: 첫 실행 때 폴더 신뢰 확인 창이 떠서 사용자가 한 번 눌러야 할 수 있음, 사용자 전역 Stop 훅이
  관리자 답마다 돌아 추가 턴을 쓸 수 있음, 대화가 쌓이면 가끔 재시작해야 함.

### 4단계 구현 메모 (2026-11-20, `voice/control.py`·`voice/hooks_install.py`·`InboxWatcher`)
- **훅 → 리스너는 파일**: `hooks/_common.py`가 `~/.voxcode/inbox/<시각>-<난수>.json`을 `.tmp` → 이름 바꾸기로 쓴다.
  리스너는 0.3초마다 `*.json`만 읽고 처리 후 지운다. 못 읽는 파일은 `inbox/bad/`. TCP 서버·포트 8765는 없어졌다.
- **켜짐 표시는 전역** `~/.voxcode/config.json` — 훅이 모든 프로젝트에서 돌아 프로젝트 파일로는 판단할 수 없다.
- **전역 훅 등록**(사용자 결정: 켤 때 등록·끌 때 해제 — 꺼 두면 다른 세션 비용 0): `voice.control on`이
  `~/.claude/settings.json`에 Stop·Notification·UserPromptSubmit 훅을 넣는다. 이 프로젝트 hooks 경로가 든 항목만
  우리 것으로 보고, 두 번 넣어도 중복 없음, 깨진 JSON이면 안 씀, 백업 `.voxcode.bak`. 프로젝트 `.claude/settings.json`의
  훅은 지웠다(겹치면 두 번 알림).
- **종료·생존 확인**: `/voice-off`는 inbox에 `shutdown` 파일을 남긴다(리스너 시작 전 신호는 무시). 살아 있음은
  `~/.voxcode/listener.alive` 갱신 시각(2초마다, 6초 넘으면 꺼진 것).
- **리스너가 켜지기 60초 넘게 전에 온 알림**은 세션 등록만 하고 읽지 않는다(꺼져 있던 동안 쌓인 요약을 몰아 읽지 않게).
- **알림 종류**: 알림마다 Jev로 완료/실패/질문/진행 중을 골라 `notice_kind`로 기록만 한다. 조용히 모드의 읽기 기준은 아직 훅 종류.
- **받아쓰는 동안 TTS 미룸**(`TtsQueue.hold`) — 마이크에 TTS 소리가 섞이지 않게.

## 구현 상태 (2026-09-26)

`voice/listener.py` **최소 버전 구현 및 실측 검증 완료**. 구현/검증된 것:
- 로컬 TCP 서버(127.0.0.1:8765) — asyncio 기반
- 세션별 상태 테이블(dict, `SessionTable`) — `upsert_from_notify`, `mark_command_sent`
- 완료 알림 → TTS 재생 큐(`TtsQueue`, threading) — "{프로젝트명}, {요약}" 형식, 여러 알림
  동시 도착 시 순서대로 순차 재생(실측: 3개 세션 가짜 알림을 순서대로 정확히 재생 확인)
- 세션 라우팅 규칙 ①~④ 전부(`route_command`), "멈춰 {프로젝트명}" 브로드캐스트/무시 규칙
  전부(`parse_stop_command`, `route_and_send`) — 유닛 테스트로 검증
- `voice/inject.js` subprocess 호출(`send_postback`) — 가짜 세션(존재하지 않는 named pipe)
  대상으로는 `connect ENOENT`로 정확히 실패, **이 세션 자신의 실제
  `CLAUDE_CODE_MESSAGING_SOCKET`/`TOKEN`으로도 실제 postback 성공 확인**(returncode 0,
  "전송 완료")
- `voice/tts.py`로 TTS 분리(sherpa-onnx, 한국어 모델 하드코딩) — 합성 실측 성공

범위 밖(스텁, TODO 주석으로 표시됨): 실시간 마이크 VAD/wakeword/STT. 대신 `route_and_send(table, text)`
함수로 텍스트를 직접 넣어 라우팅 로직만 독립적으로 검증 가능.

## 프로세스 경계와 이유

| 경계 | 이유 |
|---|---|
| 훅(Python, 짧게 실행 후 종료) ↔ 상주 프로세스(계속 떠 있음) | 훅은 Claude Code가 매번 새로 실행하는 단발성 프로세스라 무거운 모델(whisper 로딩 16.7초 등)을 매번 들고 있을 수 없음. 무거운 건 상주 프로세스가 미리 로딩해둔다 |
| 상주 프로세스(Python) → inject.js(Node) | Cross-session messaging의 실제 프로토콜(named pipe, 특정 write 방식)이 Node 환경에서 먼저 검증됐고, Claude Code 자체가 Node 기반이라 관련 예제도 Node. Python에서 Windows named pipe를 직접 다루는 것보다 검증된 Node 스크립트를 그대로 spawn하는 쪽이 리스크가 낮음 |
| 훅 → 상주 프로세스: 로컬 TCP 소켓 (파일 감시 아님) | 즉시 반응 + 상주 프로세스가 꺼져 있으면 `ConnectionRefusedError`로 바로 알 수 있음 (2026-09-25 결정) |

## 데이터 흐름 (이벤트별)

### 1. 작업 완료 → 음성 요약
1. Claude Code가 응답을 마치면 Stop 훅 실행 (`hooks/on-stop.py`)
2. 훅이 stdin JSON에서 `last_assistant_message` 필드와, 현재 작업 디렉토리(`cwd`)를 함께 읽음
2-1. **`cwd`가 `.claude/worktrees/` 아래면 훅은 아무것도 하지 않고 조용히 종료** (2026-09-27 확정, 아래 "/delegate 서브에이전트와의 관계" 참고) — `/delegate`/`/delegate-all`의 작업자(워커) 세션이 이 경로에서 도는데, `/voice-on`은 사용자가 직접 켠 관리자 세션에만 적용되는 것이 맞고 워커까지 음성 알림을 내면 마일스톤당 작업자 수만큼 알림이 쏟아짐
3. 훅이 로컬 TCP 소켓으로 상주 프로세스에 `{세션 식별자, 프로젝트명(cwd 폴더명), 요약 텍스트}`를 전달하고 즉시 종료
4. 상주 프로세스가 **"{프로젝트명}, {요약}"** 형식으로 TTS 멘트를 만들어 재생 (2026-09-26 확정 — 세션이 여러 개 겹칠 때 사람이 듣고 바로 어느 프로젝트인지 구분하기 위함. 프로젝트명은 폴더명 그대로 자동 사용, 별도 설정 불필요. 발음이 어색하면 `voice-settings.json`의 `project_alias`로 나중에 보완, 2단계로 미룸)
5. **Claude Code 공식 터미널 벨 알림을 음성 요약과 병행 재생할지 여부**는 사용자가 설정으로 켜고 끌 수 있음 — 새 비프음을 우리가 만드는 게 아니라, 이미 있는 공식 기능(벨)을 그대로 쓸지 끌지 선택하는 것. 끄는 방법은 Claude Code 자체 설정(터미널 벨 옵션)을 그대로 안내하거나, 이 프로젝트 설정에서 병행 여부만 문서화하는 두 방식 중 미정

**Claude 응답 자체가 "짧고 간결한 음성 요약" 전제였음을 재확인 (2026-09-26)**: `last_assistant_message`(=Claude가 방금 낸 응답 원문)를 그대로 TTS로 넘기는 설계이므로, 별도 요약 추출 로직(태그 파싱 등)은 만들지 않는다 — 대신 **Claude 자신이 음성모드가 켜진 프로젝트에서는 응답을 TTS로 듣기 적합하게 짧게 써야 한다**는 전제가 원래부터 깔려 있었다. 다만 이 전제가 프로젝트 `CLAUDE.md`에 실제로 반영돼 있지 않아 Claude가 매 세션에서 인지할 방법이 없었던 것이 빠진 조각.

#### 음성모드 응답 스타일 강제 — "3중 재주입" 설계 (2026-09-26 설계 확정, 우선순위 1·2 구현+실측 검증 완료)

CLAUDE.md에 지침 한 줄만 넣는 것으로는 부족하다고 판단됨 — 컨텍스트가 길어지면 실제로 그
지침을 잊는 사례가 실측으로 있었음(사용자가 "우리 이미 얘기했잖아 봐봐"라고 지적한 세션 내
실제 사례). 그래서 **같은 지침 하나**("음성모드 켜지면 응답 끝을 TTS로 듣기 적합한 1~2문장으로
맺어라")를 놓치기 쉬운 세 시점 각각에 값싸게 재주입하는 구조로 확정 — 기능 3개를 새로 만드는
게 아니라 하나의 지침을 세 시점(매 턴/세션 시작/컴팩션 후)에 반복 주입하는 것이라 최소성
원칙(YAGNI)에 어긋나지 않는다고 판단(실질 비용 차이로 아래 우선순위를 매김).

1. **`UserPromptSubmit` 훅 (핵심, 우선순위 1) — 구현+실측 검증 완료 (2026-09-26)** — `hooks/on-user-prompt-submit.py`
   - Claude Code 공식 훅. 세션당 1회가 아니라 **사용자가 메시지를 제출할 때마다 매번** 실행됨.
   - `voice/config.py`의 `is_enabled()`로 이 프로젝트의 음성모드(`enabled: true`) 여부를 확인,
     켜져 있으면 stdout에 아래 JSON을 출력하고 exit 0:
     ```json
     {
       "hookSpecificOutput": {
         "hookEventName": "UserPromptSubmit",
         "additionalContext": "[음성모드 켜짐] 이 응답의 끝은 TTS로 읽힙니다. 코드블록·파일경로 나열 없이 1~2문장의 짧고 자연스러운 한국어 요약으로 맺으세요."
       }
     }
     ```
   - 공식 문서 근거(claude-code-guide 서브에이전트로 확인): `additionalContext`는 반드시
     `hookSpecificOutput` 안에 중첩해야 하며(최상위에 두면 조용히 무시됨), Claude Code가 이를
     "Claude가 평문으로 읽는 시스템 리마인더"로 주입한다. 타임아웃 기본값 30초(다른 이벤트의

### 3. 유휴 상태에서 호출어로 명령
1. 상주 프로세스가 항상 마이크를 열어 VAD + local-wake로 "자비스" 감지 대기
2. "자비스" 감지 → 받아쓰기 모드 진입. **피드백은 TTS 문장이 아니라 짧은 비프음**(진입 시 높은 톤 1회, 인식 완료 시 낮은 톤 1회로 구분)으로 확정 (2026-09-26) — 받아쓰기는 사용자가 바로 이어 말해야 하는 타이밍이라 "네" 같은 TTS 문장은 지연·발화 겹침 위험이 있어 제외
3. 발화 종료(VAD로 침묵 감지) → 녹음된 오디오를 whisper.cpp(`language='ko'` 고정)로 텍스트화
3-1. **받아쓰기 환각 필터 (2026-11-20, 같은 날 연결 해제 — 코드만 남김)** — whisper가 무음·잡음에서 지어낸 문장을 라우팅 전에 버린다
   (`should_drop_transcript()` → `voice/judge.py`, known-issues.md 15번). 괄호 표기는 규칙, 나머지는
   Jev 판단 모델(TypeSafe)이 환각 확률을 판정(≥0.5면 버리고 낮은 비프 한 번 더). "멈춰"는 판정 생략,
   키가 없거나 오류면 통과. **키가 있으면 받아쓴 문장이 TypeSafe(미국)로 전송된다** — 사용자 승인(2026-11-20).
   아래 "LLM 판단이 개입하지 않는다"는 라우팅 규칙에 대한 것이고, 이 필터는 라우팅 앞단의 별도 단계다.
4. **어느 세션(프로젝트)으로 보낼지 판단** — 라우팅 규칙은 아래 "세션 라우팅" 확정 참고
5. 텍스트를 `voice/inject.js`로 그 세션에 postback → 해당 Claude Code 세션에 사용자 메시지로 도착
6. 기존 작업 중이었다면 중단하지 않음(2026-09-25 결정: 트리거 로직)

#### 세션 라우팅 (다중 세션 확장, 2026-09-26 확정 — 2026-11-20 "다음 설계" 1단계로 대체, 기록용)

**핵심 전제**: 상주 에이전트는 음성 명령의 **내용을 이해할 필요가 없다** — 어느 세션으로 보낼지만
정하면 되므로, 순수하게 상태 테이블 기반 규칙(타임스탬프 비교·문자열 매칭)으로 처리한다. LLM
판단이 개입하지 않는다.

**상주 프로세스가 유지하는 상태**: 세션마다 하나의 레코드.
```
{ session_id(=SOCKET 경로 자체), 프로젝트명(cwd 폴더명), socket_path, token,
  last_notify_at(마지막 완료/알림 시각), last_command_at(마지막 음성 명령 받은 시각) }
```
세션 식별자를 별도로 만들 필요 없음 — 각 세션의 `CLAUDE_CODE_MESSAGING_SOCKET` 경로 자체가 이미
고유값이라 그대로 키로 쓴다.

**라우팅 규칙 (기계적, 우선순위 순)**:
1. 발화 내용이 프로젝트명과 일치하는 단어로 시작하면(예: "eyes-free, ...") → 그 세션으로 즉시 라우팅(문자열 매칭, 오버라이드)
2. 그 외에는 **`last_notify_at`이 가장 최근인 세션**으로 라우팅 — "방금 끝난 것에 이어 말한다"는 흐름을 기본값으로 삼음
3. 방금 완료 알림이 없었고(전부 오래전) 직전에 사용자가 명령을 보낸 세션이 있으면 그 세션(`last_command_at` 최신) 유지
4. 세션이 하나뿐이면 판단 자체가 생략되고 그 세션으로 고정

이 규칙으로 위 "TTS 프로젝트명 안내"(각 완료 안내가 "{프로젝트명}, ...")와 자연스럽게 맞물린다 —
사람이 방금 들은 프로젝트명을 그대로 불러 1번 규칙을 쓰거나, 아무 말 없이 바로 이어 말하면 2번
규칙이 같은 세션으로 보내준다.

2. VAD가 발화 감지 → 호출어 없이 즉시 TTS 중단 + 받아쓰기 모드 진입
3. 이후는 위 3번 흐름과 동일

### 5. 제어 명령 ("멈춰") — 일반 명령과 다른 별도 경로 (2026-09-26 확정 — 2026-11-20 "다음 설계" 1단계로 대체, 기록용)
> **2026-11-20 대체 예정**: 위 "다음 설계"의 명령 목록으로 바뀐다 — "멈춰"는 Jev가 고른 세션 하나에만 전달하고, 전체는 "전체 멈춰"로 따로 말한다.

"멈춰"류 중단 명령은 위 "세션 라우팅"(①~④, 최근 완료/명령 세션 추정)을 쓰지 않는다. 잘못된 세션이
멈추면 상대적으로 되돌리기 까다롭기 때문에, **상주 프로세스가 추정하지 않고 판단을 각 세션에
맡긴다**:

1. STT 결과가 `"멈춰"`로 시작하되 **그 뒤에 프로젝트명(단어)이 없으면 무시** — 모호한 "멈춰"만으로는
   아무 세션도 건드리지 않는다(실수 방지, 상주 프로세스는 이 형식 검사만 하면 됨 — 의미 이해 불필요)
2. `"멈춰 {프로젝트명}"` 형식이면, 라우팅 판단 없이 **현재 열려 있는 모든 세션에 그대로 브로드캐스트**
   (각 세션의 `voice/inject.js`로 동일 텍스트를 postback)
3. 각 세션은 받은 텍스트의 프로젝트명이 **자기 자신의 프로젝트명과 일치하는지 스스로 판단**하고, 맞으면
   중단 동작을 수행, 아니면 무시. 이 판단(자기 프로젝트가 맞는지)은 상주 프로세스가 아니라 각 세션의
   Claude 자신이 한다 — "상주 에이전트는 맥락을 이해할 필요 없이 전달만 한다" 원칙을 제어 명령에도
   동일하게 적용
4. 여러 프로젝트명이 서로 부분 문자열로 겹치는 경우(예: `eyes-free-coding`과 `eyes-free-test`)는
   **각 세션이 정확 일치를 기준으로 판단하는 선까지만 기계가 책임지고, 그 이상(둘 다 정확히 일치하는
   극단적 케이스 등)은 사용자가 프로젝트명을 구분되게 부르는 재량에 맡긴다** (2026-09-26 확정) —
   자동 구분을 더 정교하게 만들려 하지 않음(과설계 방지)

  매치 시 즉시 재활성화하도록 구현. 검증은 두 층위로: ① `SessionTable`/`route_command`를 직접
  호출하는 순수 코드 테스트로 4개 시나리오(기본 라우팅→detach→재라우팅에서 제외→프로젝트명 직접
  호출로 즉시 재활성화) 전부 확인 ② 실제 리스너 프로세스를 띄워 진짜 TCP로 `notify`/`detach`/
  `attach` 이벤트를 주고받아 `handle_client`까지 왕복 확인(마이크·스피커 불필요, probe 방식).
  `/voice-off`의 지침 회수 체크리스트에도 "`active`는 리스너 프로세스 메모리에만 있어 shutdown
  시 자동으로 초기화되므로 별도 회수 불필요"임을 추가 기록(`.claude/skills/voice-off/SKILL.md`).

## `/delegate`, `/delegate-all` 서브에이전트와의 관계 (2026-09-27 확정)

**결론**: 통합 기능을 별도로 만들지 않는다. `/voice-on`은 사용자가 직접 실행하는 **세션 단위**
스킬이라, 사용자가 대화하는 "관리자 세션"에서만 켜진다. `/delegate`/`/delegate-all`이 내부적으로
띄우는 하위 작업자(워커) 세션은 사용자가 직접 켠 적이 없으므로, 음성 알림이 거기까지 번지면
안 된다.

**문제였던 지점**: 훅은 `.claude/settings.json`(Claude Code 공식 설정)에 프로젝트 전역으로
등록된다. 이 설정은 그 프로젝트 안의 **모든 세션**(관리자든 워커든)에 똑같이 적용되어, 워커
세션에도 그대로 걸린다 — 그대로 두면 마일스톤 하나에 작업자가 3~5명 붙을 때 완료 알림이
작업자 수만큼 쏟아지는 문제가 생긴다.

**해결**: 훅이 `cwd`를 확인해, `/delegate` 계열이 작업자를 격리하는 경로인
**`.claude/worktrees/` 아래이면 TCP 전송 없이 조용히 종료**한다(harness 스킬이 이미
`.git/info/exclude`에 이 경로를 등록해두는 관례와 일치하는 경로를 그대로 재사용 — 새 규칙을
만든 게 아니라 기존 관례에 올라탄 것). 관리자 세션(위 경로 밖)은 평소대로 동작한다.

이 판단으로 `/delegate` 쪽에 아무것도 새로 만들 필요가 없다 — 그 스킬은 이 프로젝트의 존재를
몰라도 되고, 이 프로젝트의 훅만 워커 여부를 스스로 판별하면 끝난다.

## 설정 파일과 프로세스 생명주기 (2026-09-26 확정)

### 설정 파일: `.claude/voice-settings.json`
`.claude/settings.json`(Claude Code 공식 설정)에 얹지 않고 **별도 파일로 분리**한다 — 공식 스키마와
섞이면 Claude Code 업데이트로 깨질 위험이 있고, 프로젝트마다 다른 음성 설정(호출어, 벨 병행 여부
등)을 자연스럽게 가질 수 있어야 하기 때문. 파일이 없으면 아래 기본값으로 동작(설치 직후 별도
설정 없이 바로 사용 가능해야 함).

```json
{
  "enabled": true,
  "wake_word": "자비스",
  "language": "ko",
  "play_official_bell": true,
  "project_alias": null
}
```

| 키 | 의미 | 기본값 |
|---|---|---|
| `enabled` | 음성모드 전역 on/off. `/voice-on`·`/voice-off`가 토글 | `false` (2026-09-27 정정 — 설치 직후 기본값이 `true`면 `/voice-on`을 켠 적 없어도 이미 켜진 것과 같아 스킬의 존재 의미가 없어짐) |
| `wake_word` | 호출어 (local-wake 온보딩 대상) | `"자비스"` |
| `language` | whisper STT 언어 코드 — 항상 명시 필요(known-issues.md 6번) | `"ko"` |
| `play_official_bell` | 완료 시 공식 터미널 벨을 음성 요약과 병행 재생할지 | `true` |
| `project_alias` | TTS로 읽을 프로젝트명. `null`이면 `cwd` 폴더명 그대로 사용 | `null` |

### 상주 프로세스 생명주기: OS 프로세스 spawn (Windows 서비스 아님)
- `/voice-on`: PID 파일 또는 고정 포트 점유 여부로 이미 떠 있는지 확인 → 없으면 `voice/listener.py`를
  분리된 백그라운드 프로세스로 spawn(`subprocess.Popen` + Windows `DETACHED_PROCESS` 플래그) →
  `voice-settings.json`의 `enabled`를 `true`로 기록
- `/voice-off`: `enabled`를 `false`로 기록 → 상주 프로세스에 로컬 TCP 소켓으로 종료 신호 전송 →
  프로세스가 스스로 정리 후 종료
- **Windows 서비스로 만들지 않는다** — 사용자가 로그인해서 실제로 코딩할 때만 필요한 도구라 상시
  구동(재부팅 후 자동 시작 등)까지는 과함. 설치 복잡도만 올라가고 얻는 이득이 없어 채택 안 함

## 경쟁/유사 프로젝트 조사 (밤모드, 2026-09-26)

  quietly summarises the others, each gets a distinct voice") — 이 프로젝트의 "선착순 큐"보다
  진전된 기능. 단 **macOS 14+ 전용, Windows 미지원**.
- **AgentsRoom**, **claude-voice** 등도 유사 시도 있으나 각각 범위/플랫폼 제약 있음.
- **Talon Voice/Cursorless**는 "코드를 음성으로 받아쓰기"가 목적이라 이 프로젝트(에이전트에게
  지시하고 완료를 듣기)와 카테고리 자체가 다름 — 직접 경쟁 아님.

**수요 신호**: `anthropics/claude-code#50720`("JARVIS-style voice-to-voice hands-free mode")이
정확히 이 프로젝트가 노리는 것(연속 대화, 응답 음성 읽기, barge-in)을 요청했으나 **Anthropic이
"not planned"로 공식 종료** — 서드파티 애드온의 존재 이유가 명확해짐. `#42700`도 같은 수요 제기.

**차별점**: 조사된 경쟁자 중 **Windows를 실제로 잘 지원하는 프로젝트가 없음**(VoxHerd는 브릿지만
Windows 주장, Heard/claude-voice는 macOS 전용). 이 프로젝트가 Windows + 완전 로컬(sherpa-onnx +
whisper.cpp)을 완성하면 그 조합 자체가 거의 비어 있는 틈새.

**뒤처진 지점(향후 검토 대상)**: 다중 세션 중 우선순위 판단(Heard가 이미 구현, 이 프로젝트는 아직
"도착 순"만), 모바일에서 원격 제어(VoxHerd), 공식 `/voice`(STT 입력)와의 통합/보완 전략 미정.

Sources: https://voxherd.com/, https://github.com/heardlabs/heard, https://agentsroom.dev/features/voice-mode, https://github.com/Syntic-Ai/claude-voice, https://github.com/anthropics/claude-code/issues/50720, https://github.com/anthropics/claude-code/issues/42700

## Heard 심화 조사에서 나온 역제안 (밤모드, 2026-09-26, 설계 스케치만 — 미착수)

경쟁 프로젝트 조사(위 절)에서 이름만 적어두고 넘어갔던 Heard의 실제 README를 다시 읽어
아래 두 기능을 구체적으로 이식할 수 있는지 스케치했다. **아직 어떤 코드도 바꾸지 않았다** —
"최종 채택 여부"는 큰 결정이라 사용자 확인 후로 미룬다.

### 1. "Catch me up" — 자리 비운 동안의 요약을 나중에 몰아서 듣기 (2026-09-26 설계 확정, 미착수)
> **2026-11-20 대체**: "다음 설계"의 "밀린 거 듣기" 명령으로 흡수 — 아무 세션에 부탁하는 대신 `log.jsonl`을 서브 관리자가 요약한다.

Heard는 완료 즉시 읽어주는 것과 별개로, 사용자가 "캐치 미 업"이라고 말하면 그 사이 여러
세션에서 일어난 일을 **다시 요약**해 들려준다(오래된 개별 알림을 그대로 재생하지 않고,
전부 다시 압축). 지금 이 프로젝트는 "완료 즉시 큐에 쌓아 순서대로 재생"만 있어서, 알림을
놓치면(예: 다른 방에 있었음) 그냥 사라진다.

**재요약 방식 확정**: 별도 API 키나 상시 대기 세션 없이, **기존 라우팅 규칙으로 선택된
아무 살아있는 세션에게 그냥 파일을 읽고 요약해달라고 부탁**한다 — Anthropic API를
리스너가 직접 호출하는 방식(A안)과 관리자 세션에 위임하는 방식(B안) 둘 다 검토했으나,
결국 "지금 응답 가능한 세션에게 파일 경로를 주고 부탁하면 그만"이라는 훨씬 단순한 방식으로
확정(2026-09-26 사용자 논의). 이 방식은 `/delegate`가 서브에이전트에게 작업을 위임하는
것과 본질적으로 같은 패턴이지만, Agent 도구를 명시적으로 쓸 필요도 없이 그냥 평소 명령
라우팅 경로(inject.js → 세션 프롬프트)를 그대로 재사용한다.

**흐름**:
1. `voice/listener.py`가 완료 이벤트마다 이력을 `.scratch/history/pending.jsonl`에
   `{timestamp, project_name, summary}` 형태로 계속 append.
2. "캐치 미 업"류 특수 명령이 STT로 인식되면, `_dictation_cycle`이 일반 라우팅 대신
   이 명령을 감지하는 분기를 먼저 탐(`parse_stop_command`와 비슷한 위치) — 감지되면
   기존 라우팅 규칙(①~④) 그대로 세션 하나를 고른 뒤, 그 세션에 아래 프롬프트를 inject:
   > "자리 비운 동안 쌓인 작업 이력이 `.scratch/history/pending.jsonl`에 있습니다.
   > 읽고 짧게 요약해서 그 파일을 정리한 뒤, 사용자에게는 핵심만 답해주세요."
3. 세션이 원본 이력을 읽고 압축된 요약으로 **같은 파일을 정리**(원본 로그 그대로 쌓이지
   않고 계속 짧게 유지됨 — 파일이 무한정 커지지 않음), 사용자에게는 짧은 핵심만 응답.
4. 그 응답은 기존 Stop 훅 → TCP → TTS 큐 경로를 그대로 타고 재생됨 — 새 재생 경로 불필요.

- **영향 범위**: `voice/listener.py`(이력 append 로직, "캐치 미 업" 명령 감지 분기),
  이력 파일 경로 상수 하나. 세션 쪽 CLAUDE.md/스킬 지침에 "파일 정리" 요청을 받았을 때의
  동작 방식을 명시할 필요는 없음 — 프롬프트 자체에 이미 전부 담겨 있어 별도 지침 불필요.
- **난이도**: 중간 — 새 데이터 구조(이력 파일) 하나 + 새 명령 파싱 분기 하나, 기존
  TCP/TTS/라우팅 파이프라인을 그대로 재사용해 실제 구현 범위는 처음 가늠보다 작아짐.

### 2. Listening modes (Co-pilot / Companion / Focus) — 상황별 알림 상세도 (2026-09-26 자동판단 보류 확정)
> **2026-11-20 대체**: "다음 설계"의 "조용히 / 다 알려줘" 수동 전환으로 흡수.

Heard는 "화면 보는 중(짧게)/손 뗀 상태(자세히)/집중 중(알림만)" 3모드를 사용자가 전환하면
같은 이벤트도 다르게 말해준다. 지금 이 프로젝트는 항상 "{프로젝트명}, {요약}" 한 형식뿐이라,
접근성 사용자(화면을 아예 못 보는)와 "다른 일 하며 지휘"(가끔 확인) 사용자가 원하는 상세도가
다를 수 있다는 점을 반영 못 하고 있음 — 이 프로젝트의 두 핵심 시나리오(접근성 vs 비서형
멀티태스킹)에 정확히 대응되는 축이라 특히 눈여겨볼 만함.

**핵심 쟁점과 결론(2026-09-26 사용자 논의)**: "지금 사용자가 화면을 보는 중인지/손을 뗀
상태인지/집중 중인지"를 **자동으로 판단하는 방법이 마땅치 않다** — Heard(macOS)는 OS
레벨 API(화면 잠금 상태, 포커스 모드 등)로 이를 추론하지만, Windows에서 비슷한 수준의
자동 감지를 구현하는 건 이 프로젝트의 "가벼운 애드온" 지향과 비교해 공수가 크다.
**결론: 자동 판단은 보류하고, 사용자가 음성 명령("집중 모드로 바꿔줘" 등)이나 스킬로
직접 모드를 전환하는 수동 방식만 남긴다.** 이마저도 두 기능(Catch me up 포함)을 완성한
뒤 다시 고려하기로 함 — 지금은 스케치만, 착수는 나중.

- **영향 범위(수동 전환 기준)**: `.claude/voice-settings.json`에 `listening_mode` 키 추가(예:
  `"focus"|"copilot"|"companion"`), `voice/listener.py`의 TTS 큐가 재생 전에 모드별로
  요약 텍스트를 다르게 구성(focus는 실패/승인 대기만 소리 내고 나머지는 조용히 로그만).
  세션 쪽 CLAUDE.md 3중 재주입 지침도 모드별로 다른 "몇 문장까지"를 요구하게 갈라질 수 있음.
  새 스킬(`/voice-mode <모드>` 등) 또는 음성 명령 파싱 분기 하나 필요.
- **난이도**: 낮음~중간(수동 전환 기준) — 설정 키 하나 + 재생 큐 필터링 로직, 기존 구조를
  크게 안 건드림. 단, "focus 모드에서 뭘 승인 대기로 볼지" 판단 로직은 필요.
- **자동 감지(화면 잠금 여부 등)는 완전히 보류** — 기록만 남기고 설계도 진행 안 함.

### 참고 — 기각했던 B안과의 재연결
`docs/architecture.md`(구 버전)에서 "저비용 모델 전용 판단 세션에 라우팅 위임"을 B안으로
고려만 하고 A안(세션 자기 상태 관리)을 채택했었다. Heard의 "narration brain"(이벤트를 최근
컨텍스트+활성 에이전트 목록과 대조해 판단하는 별도 LLM 패스)이 정확히 이 B안 방식이고,
실제 프로덕션에서 쓰이고 있다는 게 이번에 확인됨 — 다중 세션 우선순위 판단(위 "뒤처진 지점")을
나중에 구현할 때 A안 확장(각 세션이 알아서 판단)보다 B안(중앙 판단자)이 더 맞을 수 있다는
근거가 하나 늘었다. 지금 당장 결정하지 않고 기록만.
