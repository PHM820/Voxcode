# 전체 아키텍처

`docs/decisions.md`에 흩어진 결정들을 하나의 그림으로 묶은 문서.
세부 근거·실측 수치는 각 결정 항목을 참고하고, 여기서는 "무엇이 무엇을 어떻게 부르는지"만 다룬다.

## 프로젝트 성격 (2026-09-26 재정의)

이 프로젝트는 "눈이 안 좋은 사람"에 국한되지 않는다. 기본 가치는 **화면을 안 보고도 여러 프로젝트를
동시에 음성으로 지휘하는 비서** — 접근성은 그 일반 기능의 자연스러운 부분집합이다. 사용자가 다른
작업을 하며 여러 Claude Code 세션(프로젝트별)에 음성으로 지시하고, 각 세션이 끝날 때마다 상주
에이전트 하나가 순차적으로 음성 요약을 들려주고, 음성 명령은 올바른 세션으로 라우팅한다.

## 전체 그림 (다중 세션 버전)

```
┌───────────────────┐  ┌───────────────────┐  ┌───────────────────┐
│ Claude Code 세션 A │  │ Claude Code 세션 B │  │ Claude Code 세션 C │
│ (프로젝트 A)        │  │ (프로젝트 B)        │  │ (프로젝트 C)        │
│  Stop/Notification │  │  Stop/Notification │  │  Stop/Notification │
│  훅 실행             │  │  훅 실행             │  │  훅 실행             │
└─────────┬──────────┘  └─────────┬──────────┘  └─────────┬──────────┘
          │ 로컬 TCP 소켓으로 "세션 식별자 + 요약 텍스트" 전달 (동일 고정 포트, 다건 동시 가능)
          └───────────────────────┼───────────────────────┘
                                  ▼
┌─────────────────────────────────────────────────────────────┐
│  상주 리스너 프로세스  voice/listener.py  (컴퓨터에 하나만)        │
│                                                                │
│  - 로컬 TCP 서버: 여러 세션으로부터 오는 이벤트를 동시에 수신          │
│  - 세션별 CLAUDE_CODE_MESSAGING_SOCKET/TOKEN을 세션 식별자로     │
│    매핑해 기억 (각 훅이 자기 세션의 소켓 경로를 함께 보냄)           │
│  - 완료 이벤트가 여러 개 겹치면 **재생 큐**에 순서대로 쌓아 하나씩   │
│    TTS로 순차 안내 ("프로젝트 A 작업 끝났습니다" 식으로 구분)        │
│  - 항상 마이크 열어두고 VAD(Silero) + 호출어 감지(local-wake)     │
│  - 호출어 감지("자비스") → 받아쓰기 모드 → STT(whisper.cpp)       │
│  - STT 결과를 **어느 세션으로 보낼지 판단**(라우팅, 아래 참고)      │
│    → voice/inject.js로 그 세션의 소켓에 postback                │
│  - 상태 관리: 세션별 유휴/재생중/받아쓰기중 (프로세스 하나가 여러  │
│    세션 상태를 맵으로 관리)                                      │
└─────────────────────────────────────────────────────────────┘
          │ (STT 결과 postback, 대상 세션의 소켓 정보로 node 프로세스 spawn)
          ▼
┌─────────────────────────────────────────────────────────────┐
│  voice/inject.js (Node, 상주 프로세스가 필요할 때마다 실행)        │
│  - 인자로 받은 대상 세션의 SOCKET/TOKEN으로 named pipe 연결       │
│  - auth+user 두 줄을 한 번의 write()로 합쳐 전송 (검증된 프로토콜) │
└─────────────────────────────────────────────────────────────┘
```

단일 세션(프로젝트 하나만 열어놓고 쓰는 경우)은 이 다이어그램에서 "세션이 하나뿐인 특수한 경우"로
그대로 동작 — 별도 모드 분기 없이 자연스럽게 축소된다.

## 구현 상태 (2026-09-26)

`voice/listener.py` **최소 버전 구현 및 실측 검증 완료**. 구현/검증된 것:
- 로컬 TCP 서버(127.0.0.1:8765) — asyncio 기반
- 세션별 상태 테이블(dict, `SessionTable`) — `upsert_from_notify`, `mark_command_sent`
- 완료 알림 → TTS 재생 큐(`TtsQueue`, threading) — "{프로젝트명}, {요약}" 형식, 여러 알림
  동시 도착 시 순서대로 순차 재생(실측: 3개 세션 가짜 알림을 순서대로 정확히 재생 확인)
- 세션 라우팅 규칙 ①~④ 전부(`route_command`), "멈춰 {프로젝트명}" 브로드캐스트/무시 규칙
  전부(`parse_stop_command`, `route_and_send`) — 유닛 테스트로 검증
- `voice/inject.js` subprocess 호출(`send_postback`) — 가짜 세션(존재하지 않는 named pipe)
  대상으로는 `connect ENOENT`로 정확히 실패, **이 세션 자신의 실제
  `CLAUDE_CODE_MESSAGING_SOCKET`/`TOKEN`으로도 실제 postback 성공 확인**(returncode 0,
  "전송 완료")
- `voice/tts.py`로 TTS 분리(sherpa-onnx, 한국어 모델 하드코딩) — 합성 실측 성공

범위 밖(스텁, TODO 주석으로 표시됨): 실시간 마이크 VAD/wakeword/STT. 대신 `route_and_send(table, text)`
함수로 텍스트를 직접 넣어 라우팅 로직만 독립적으로 검증 가능.

## 프로세스 경계와 이유

| 경계 | 이유 |
|---|---|
| 훅(Python, 짧게 실행 후 종료) ↔ 상주 프로세스(계속 떠 있음) | 훅은 Claude Code가 매번 새로 실행하는 단발성 프로세스라 무거운 모델(whisper 로딩 16.7초 등)을 매번 들고 있을 수 없음. 무거운 건 상주 프로세스가 미리 로딩해둔다 |
| 상주 프로세스(Python) → inject.js(Node) | Cross-session messaging의 실제 프로토콜(named pipe, 특정 write 방식)이 Node 환경에서 먼저 검증됐고, Claude Code 자체가 Node 기반이라 관련 예제도 Node. Python에서 Windows named pipe를 직접 다루는 것보다 검증된 Node 스크립트를 그대로 spawn하는 쪽이 리스크가 낮음 |
| 훅 → 상주 프로세스: 로컬 TCP 소켓 (파일 감시 아님) | 즉시 반응 + 상주 프로세스가 꺼져 있으면 `ConnectionRefusedError`로 바로 알 수 있음 (2026-09-25 결정) |

## 데이터 흐름 (이벤트별)

### 1. 작업 완료 → 음성 요약
1. Claude Code가 응답을 마치면 Stop 훅 실행 (`hooks/on-stop.py`)
2. 훅이 stdin JSON에서 `last_assistant_message` 필드와, 현재 작업 디렉토리(`cwd`)를 함께 읽음
3. 훅이 로컬 TCP 소켓으로 상주 프로세스에 `{세션 식별자, 프로젝트명(cwd 폴더명), 요약 텍스트}`를 전달하고 즉시 종료
4. 상주 프로세스가 **"{프로젝트명}, {요약}"** 형식으로 TTS 멘트를 만들어 재생 (2026-09-26 확정 — 세션이 여러 개 겹칠 때 사람이 듣고 바로 어느 프로젝트인지 구분하기 위함. 프로젝트명은 폴더명 그대로 자동 사용, 별도 설정 불필요. 발음이 어색하면 `voice-settings.json`의 `project_alias`로 나중에 보완, 2단계로 미룸)
5. **Claude Code 공식 터미널 벨 알림을 음성 요약과 병행 재생할지 여부**는 사용자가 설정으로 켜고 끌 수 있음 — 새 비프음을 우리가 만드는 게 아니라, 이미 있는 공식 기능(벨)을 그대로 쓸지 끌지 선택하는 것. 끄는 방법은 Claude Code 자체 설정(터미널 벨 옵션)을 그대로 안내하거나, 이 프로젝트 설정에서 병행 여부만 문서화하는 두 방식 중 미정

### 2. 권한 요청 → 알림
- 동일 구조, `hooks/on-notification.py` → 상주 프로세스 → "{프로젝트명}, {안내}" 형식으로 짧은 TTS 안내

### 3. 유휴 상태에서 호출어로 명령
1. 상주 프로세스가 항상 마이크를 열어 VAD + local-wake로 "자비스" 감지 대기
2. "자비스" 감지 → 받아쓰기 모드 진입. **피드백은 TTS 문장이 아니라 짧은 비프음**(진입 시 높은 톤 1회, 인식 완료 시 낮은 톤 1회로 구분)으로 확정 (2026-09-26) — 받아쓰기는 사용자가 바로 이어 말해야 하는 타이밍이라 "네" 같은 TTS 문장은 지연·발화 겹침 위험이 있어 제외
3. 발화 종료(VAD로 침묵 감지) → 녹음된 오디오를 whisper.cpp(`language='ko'` 고정)로 텍스트화
4. **어느 세션(프로젝트)으로 보낼지 판단** — 라우팅 규칙은 아래 "세션 라우팅" 확정 참고
5. 텍스트를 `voice/inject.js`로 그 세션에 postback → 해당 Claude Code 세션에 사용자 메시지로 도착
6. 기존 작업 중이었다면 중단하지 않음(2026-09-25 결정: 트리거 로직)

#### 세션 라우팅 (다중 세션 확장, 2026-09-26 확정)

**핵심 전제**: 상주 에이전트는 음성 명령의 **내용을 이해할 필요가 없다** — 어느 세션으로 보낼지만
정하면 되므로, 순수하게 상태 테이블 기반 규칙(타임스탬프 비교·문자열 매칭)으로 처리한다. LLM
판단이 개입하지 않는다.

**상주 프로세스가 유지하는 상태**: 세션마다 하나의 레코드.
```
{ session_id(=SOCKET 경로 자체), 프로젝트명(cwd 폴더명), socket_path, token,
  last_notify_at(마지막 완료/알림 시각), last_command_at(마지막 음성 명령 받은 시각) }
```
세션 식별자를 별도로 만들 필요 없음 — 각 세션의 `CLAUDE_CODE_MESSAGING_SOCKET` 경로 자체가 이미
고유값이라 그대로 키로 쓴다.

**라우팅 규칙 (기계적, 우선순위 순)**:
1. 발화 내용이 프로젝트명과 일치하는 단어로 시작하면(예: "eyes-free, ...") → 그 세션으로 즉시 라우팅(문자열 매칭, 오버라이드)
2. 그 외에는 **`last_notify_at`이 가장 최근인 세션**으로 라우팅 — "방금 끝난 것에 이어 말한다"는 흐름을 기본값으로 삼음
3. 방금 완료 알림이 없었고(전부 오래전) 직전에 사용자가 명령을 보낸 세션이 있으면 그 세션(`last_command_at` 최신) 유지
4. 세션이 하나뿐이면 판단 자체가 생략되고 그 세션으로 고정

이 규칙으로 위 "TTS 프로젝트명 안내"(각 완료 안내가 "{프로젝트명}, ...")와 자연스럽게 맞물린다 —
사람이 방금 들은 프로젝트명을 그대로 불러 1번 규칙을 쓰거나, 아무 말 없이 바로 이어 말하면 2번
규칙이 같은 세션으로 보내준다.

### 4. TTS 재생 중 사용자가 말을 시작 (바지-인)
1. 상주 프로세스가 TTS 재생 중에도 VAD를 계속 돌림
2. VAD가 발화 감지 → 호출어 없이 즉시 TTS 중단 + 받아쓰기 모드 진입
3. 이후는 위 3번 흐름과 동일

### 5. 제어 명령 ("멈춰") — 일반 명령과 다른 별도 경로 (2026-09-26 확정)
"멈춰"류 중단 명령은 위 "세션 라우팅"(①~④, 최근 완료/명령 세션 추정)을 쓰지 않는다. 잘못된 세션이
멈추면 상대적으로 되돌리기 까다롭기 때문에, **상주 프로세스가 추정하지 않고 판단을 각 세션에
맡긴다**:

1. STT 결과가 `"멈춰"`로 시작하되 **그 뒤에 프로젝트명(단어)이 없으면 무시** — 모호한 "멈춰"만으로는
   아무 세션도 건드리지 않는다(실수 방지, 상주 프로세스는 이 형식 검사만 하면 됨 — 의미 이해 불필요)
2. `"멈춰 {프로젝트명}"` 형식이면, 라우팅 판단 없이 **현재 열려 있는 모든 세션에 그대로 브로드캐스트**
   (각 세션의 `voice/inject.js`로 동일 텍스트를 postback)
3. 각 세션은 받은 텍스트의 프로젝트명이 **자기 자신의 프로젝트명과 일치하는지 스스로 판단**하고, 맞으면
   중단 동작을 수행, 아니면 무시. 이 판단(자기 프로젝트가 맞는지)은 상주 프로세스가 아니라 각 세션의
   Claude 자신이 한다 — "상주 에이전트는 맥락을 이해할 필요 없이 전달만 한다" 원칙을 제어 명령에도
   동일하게 적용
4. 여러 프로젝트명이 서로 부분 문자열로 겹치는 경우(예: `eyes-free-coding`과 `eyes-free-test`)는
   **각 세션이 정확 일치를 기준으로 판단하는 선까지만 기계가 책임지고, 그 이상(둘 다 정확히 일치하는
   극단적 케이스 등)은 사용자가 프로젝트명을 구분되게 부르는 재량에 맡긴다** (2026-09-26 확정) —
   자동 구분을 더 정교하게 만들려 하지 않음(과설계 방지)

## 아직 정해지지 않은 것 (다음 설계 대상)

| 항목 | 현재 상태 |
|---|---|
| 음성 명령을 여러 열린 세션 중 어디로 라우팅할지 | **규칙 확정** (2026-09-26). 위 "세션 라우팅" 참고 — 프로젝트명 언급 우선, 없으면 최근 완료 세션 |
| 여러 세션이 동시에 완료됐을 때 TTS 재생 큐 순서와 구분 멘트 문구 | **형식 확정**: "{프로젝트명}, {요약}", 순서는 도착 순(선착순)으로 충분 — 우선순위 개념은 실사용 후 필요하면 추가 |
| 로컬 TCP 소켓 메시지에 세션 식별자를 어떤 형태로 담을지 | **확정**: 별도 uuid 없이 세션의 `CLAUDE_CODE_MESSAGING_SOCKET` 경로 자체를 키로 사용 |
| 로컬 TCP 소켓 포트 번호, 메시지 포맷(JSON 스키마 필드 이름) | **확정** (2026-09-26, `voice/listener.py` 최소 버전 구현 시): 포트 `8765`(127.0.0.1 고정). 메시지 스키마: `{"event": "notify"｜"command", "session_id": "<CLAUDE_CODE_MESSAGING_SOCKET 경로>", "project_name": "<cwd 폴더명>", "text": "<요약/명령 텍스트>", "socket_path": "<postback 대상 소켓>", "token": "<postback용 토큰>"}`. `session_id`와 `socket_path`는 현재는 같은 값이지만 의미가 달라(테이블 키 vs 실제 연결 주소) 필드를 분리해 유지. 상세: `voice/listener.py` 상단 주석 |

## 설정 파일과 프로세스 생명주기 (2026-09-26 확정)

### 설정 파일: `.claude/voice-settings.json`
`.claude/settings.json`(Claude Code 공식 설정)에 얹지 않고 **별도 파일로 분리**한다 — 공식 스키마와
섞이면 Claude Code 업데이트로 깨질 위험이 있고, 프로젝트마다 다른 음성 설정(호출어, 벨 병행 여부
등)을 자연스럽게 가질 수 있어야 하기 때문. 파일이 없으면 아래 기본값으로 동작(설치 직후 별도
설정 없이 바로 사용 가능해야 함).

```json
{
  "enabled": true,
  "wake_word": "자비스",
  "language": "ko",
  "play_official_bell": true,
  "project_alias": null
}
```

| 키 | 의미 | 기본값 |
|---|---|---|
| `enabled` | 음성모드 전역 on/off. `/voice-on`·`/voice-off`가 토글 | `true` |
| `wake_word` | 호출어 (local-wake 온보딩 대상) | `"자비스"` |
| `language` | whisper STT 언어 코드 — 항상 명시 필요(known-issues.md 6번) | `"ko"` |
| `play_official_bell` | 완료 시 공식 터미널 벨을 음성 요약과 병행 재생할지 | `true` |
| `project_alias` | TTS로 읽을 프로젝트명. `null`이면 `cwd` 폴더명 그대로 사용 | `null` |

### 상주 프로세스 생명주기: OS 프로세스 spawn (Windows 서비스 아님)
- `/voice-on`: PID 파일 또는 고정 포트 점유 여부로 이미 떠 있는지 확인 → 없으면 `voice/listener.py`를
  분리된 백그라운드 프로세스로 spawn(`subprocess.Popen` + Windows `DETACHED_PROCESS` 플래그) →
  `voice-settings.json`의 `enabled`를 `true`로 기록
- `/voice-off`: `enabled`를 `false`로 기록 → 상주 프로세스에 로컬 TCP 소켓으로 종료 신호 전송 →
  프로세스가 스스로 정리 후 종료
- **Windows 서비스로 만들지 않는다** — 사용자가 로그인해서 실제로 코딩할 때만 필요한 도구라 상시
  구동(재부팅 후 자동 시작 등)까지는 과함. 설치 복잡도만 올라가고 얻는 이득이 없어 채택 안 함
